# 工作流、产物与状态恢复

## 1. 项目组织

在用户指定的 `WORK_DIR` 中按需建立以下结构；已有项目保持原有约定，不强制迁移。

```text
WORK_DIR/
├── source/                 # 原始题面、附件、官方规则快照；只读保存
├── state/                  # 当前阶段、决策、阻塞和审查记录
├── data/                   # 可重放的中间数据；不覆盖 source
├── code/                   # 数据、模型、求解、验证、绘图模块
├── runs/                   # 每次正式运行的独立目录和日志
├── results/                # 供论文使用的已核对结果索引
├── figures/                # 图形及其源数据
├── paper/                  # 论文源文件、参考文献、披露材料
└── review/                 # 质量门、问题清单和交付审查
```

不要为了符合模板而移动用户原始文件。无法创建目录时，在回复中使用同等逻辑结构。

## 2. 状态最小集合

维护简洁、可恢复的 `state/project_state.json` 或等价 Markdown，包含：

- `competition`、`year`、`problem`、`language`、`deadline`；
- `mode`、`current_stage`、`requirements_count`；
- 每问状态：`pending/designed/implemented/executed/verified/blocked`；
- 当前模型、基线、主要假设、关键参数和对应产物路径；
- 未解决的 P0/P1、证据缺口、下次行动；
- 官方规则核验时间与来源；未知值写 `null`，不猜测。

不要为记录而记录。状态服务于续做、影响分析和防伪造，不要求用户手工编辑 JSON。

## 3. 阶段契约

### Stage 0：规则与输入

输入：题面、附件、用户目标、当届规则。
输出：规则核验状态、环境能力、文件清单、模式。
通过条件：题面可读；缺失内容已列出；不把历史规则当本届规则。

### Stage 1：题意与数据

输出：Requirement Matrix、数据字典、依赖图、题型路由、歧义与解释。
通过条件：每个明确要求均有产物和验证位置；数据字段和单位有依据；问题数量来自题面。

### Stage 2：模型设计

输出：基线、候选比较、Model Card、假设台账、符号表、公式、算法和验证计划。
通过条件：模型与问题结构匹配；核心假设有理由；复杂度有增量价值；没有无法估计的关键参数被当成已知。

### Stage 3：实现与运行

输出：代码、环境说明、每次运行清单、原始输出、错误日志和结果索引。
通过条件：已知答案测试通过；真实运行存在；随机过程记录种子；失败运行与正式结果分离。

### Stage 4：验证与不确定性

输出：Verification、Validation、误差、灵敏度、鲁棒性、不确定性及结论边界。
通过条件：至少一种检查能够暴露核心模型的合理错误；灵敏度触及主要结论；没有将拟合误差当作全部可信度。

### Stage 5：写作

输出：完整初稿、摘要、图表、引用、AI 披露材料、非技术备忘录（若题目要求）。
通过条件：每问有明确答案；数字可追溯；摘要独立可读；图表和正文相互解释。

### Stage 6：终审与交付

输出：问题清单、修复记录、回归检查、格式检查、剩余风险和实际交付文件。
通过条件：无未披露 P0；P1 已处理；论文与代码结果一致；不把编译成功或内部高分当作提交保证。

## 4. 自主推进与人工决策

默认不因普通模型选择而暂停。需要用户介入的情况仅限：

- 题面或关键附件无法读取；
- 多个解释会产生根本不同且无法检验的模型；
- 官方规则无法确认且可能影响合规；
- 剩余时间迫使在“完整基线”和“高风险增强”之间选择；
- 用户明确要求引导模式或逐阶段确认。

可继续时采用最保守、可逆、证据依赖最少的方案，并记录假设。不得将沉默描述为用户批准。

## 5. 证据缺口协议

发现缺口时记录：

```text
EVIDENCE_GAP | 编号 | 缺失证据 | 影响要求/结论 | 当前严重度 | 补齐方式 | 可接受的降级结论 | 状态
```

消费该证据时必须三选一：补齐证据、删除论点、降低结论强度并披露。不得将缺口从清单删除而不处理。

## 6. 运行与结果管理

每次正式运行记录：时间、命令、代码版本或哈希、输入哈希、参数、种子、环境、输出路径、退出状态和警告。

使用新运行目录保存重跑结果；只有成功且检查通过的后代结果才能取代旧结果。失败探索可用于诊断，但不能进入论文证据链。

结果索引至少包含：`question`、`claim`、`value_or_file`、`run_id`、`status`、`verification`、`notes`。正文引用结果索引，不手工复制互相不一致的数字。

## 7. 影响分析与返工

建立依赖链：

```text
题面解释 → 数据清洗 → 参数/假设 → 模型 → 运行 → 验证 → 图表 → 小问结论 → 摘要/建议
```

任一节点改变时，列出全部下游节点并重跑或复核。修复必须针对失败机制，而非只修复触发它的单个样例。

- 数据错误：回到数据阶段，重新评估所有受影响参数和结果。
- 公式或模型错误：回到设计阶段，重新进行实现测试和现实验证。
- 代码错误：修复实现，先用已知答案回归，再正式重跑。
- 证据不足：补实验、删主张或降低结论强度。
- 表达错误：在数学和结果不变时做局部修订，不重跑无关计算。

## 8. 时间与预算降级

优先顺序：合规与完整回答 > 数学正确 > 真实求解 > 核心验证 > 清晰表达 > 可选增强。

首版应覆盖全部小问。预算不足时依次取消装饰性图表、非关键扩展、低价值候选模型和额外附录；不得取消核心正确性检查来换取复杂模型。

任何评分、迭代次数或时间比例均为内部管理工具，不是官方标准。
