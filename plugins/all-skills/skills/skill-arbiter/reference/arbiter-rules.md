# Arbiter 规则参考 V9.0

本参考扩展 `SKILL.md`，不替代其三条铁律与八层顺序。所有判断只基于用户粘贴文本；不确定时采用更弱结论并进入人工复核。

## 1. 证据与置信度

### 1.1 证据引用

- 摘录能支持判断的逐字最短充分片段，不改写、不补全缺失条件。
- 附 `skill`、规则 ID、章节标题、起止行号；无行号时附章节标题与段落序号。
- 同一路径多条规则共享来源位置时，用规则 ID 区分原子动作。
- `contradictory` 必须同时引用双方；`dependency-conflict` 另列字段/时序；`intent-conflict` 逐项列信号证据。
- 截断、缺字段或未提供材料不是否定事实。低置信结论只能疑似或待人工。

### 1.2 置信度锚点

| 值 | 标准 | 可用结论 |
|---|---|---|
| `certain` | 原文形式化、条件完备，存在可机械验证的不可同时满足关系 | 可支持强判定，仍须对抗复核 |
| `high` | 双方原文完整、范围明确，合理替代解释均已排除 | 可满足熔断置信门槛 |
| `medium` | 主要证据存在，但范围或语义仍有有限歧义 | 不得单独触发熔断 |
| `low` | 截断、骨架、指纹或关键上下文缺失 | 只能疑似/待人工 |

严重度描述影响，置信度描述证据；二者不得互相替代。

## 2. 六类关系

按 `exclusive → shared → entangled → contradictory → dependency-conflict → intent-conflict` 顺序判定。一个规则对只设一个主关系。

### 2.1 `exclusive`

- **信号**：另一技能不存在同主题、同对象或可比较约束。
- **反例**：仅措辞不同但语义等价，应判 `shared`。
- **保守默认**：主题对应关系不清时标待人工，不把“没找到”当作“明确没有”。
- **处置**：原样保留并标来源。

### 2.2 `shared`

- **信号**：规范化后语义等价，或一方要求完全包含另一方且更严格。
- **反例**：双方适用范围不同且可能产生不同结果，应考虑 `entangled`。
- **保守默认**：无法证明包含关系时保留双方并待人工，不去重。
- **处置**：保留更严格者；严格度相同取范围更窄且更精确者；再相同取规范化文本 Unicode 字典序较小者。文本仍完全相同且来源选择影响 provenance 时 `defer-human`，不得新增来源名称优先级。涉及安全规则时，还须证明去重不缩小安全覆盖；否则保留宽范围兜底并待人工。

### 2.3 `entangled`

- **信号**：存在明确输出或执行安排同时满足双方，但必须协调顺序、位置、结构或触发范围。
- **反例**：任何安排都违反至少一条，才进入 `contradictory` 评估。
- **保守默认**：先尝试分区、排序、条件化，不能把协调成本当硬矛盾。
- **处置**：双方保留，在决策规则中写清协调方式。

### 2.4 `contradictory`

- **信号**：任务、作用域、输出位置/字段/约束相同，且所有合理解释均不能同时满足。
- **反例**：A 要求“报告首行是标题”，B 要求“代码块首行是语言标记”，作用域不同，不冲突。
- **保守默认**：条件未对齐、文本截断或存在可行反方解释时降级。
- **处置**：按 S0/S1 纪律修复、隔离或拒绝；附双方原文与申诉路径。

### 2.5 `dependency-conflict`

- **信号**：同名接口的必填参数集合不一致、字段类型不兼容、默认值导致互斥行为、返回类型不兼容或调用时序相反。
- **反例**：只有工具同名，或可选字段不同但调用兼容。
- **保守默认**：缺 schema 时标依赖风险，不判确定冲突。
- **处置**：明确统一接口后合并；否则子技能隔离或拒绝。

### 2.6 `intent-conflict`

- **信号**：至少两项独立量化信号，且每项均有双方原文。
- **反例**：仅“详细”对“简洁”，或同一原文被重复算成长度与详略两项。
- **保守默认**：0–1 项只标 `style-tension-unconfirmed`，最高 S3。
- **处置**：双模式或 Router，不默认阻断。

## 3. Intent 量化表

| 信号 | 成立条件 | 证据与计算 |
|---|---|---|
| 输出长度 | 明确上限小于另一方可计算最小结构长度 | 行/字/段上限、最小段落和计算式 |
| 注释密度 | 所有代码逐行注释 vs 明确零注释/禁注释 | 双方代码注释约束原文 |
| 详略对冲 | 明确逐步解释 vs 明确不解释/只给结果 | 独立规范句，不用标题臆测 |
| 示例数量 | 每条规则示例 vs 总输出限制，且不可容纳 | 规则数、最少示例规模、上限计算 |

同一原文不得重复计两项。模糊词最多一个弱信号；Intent 冲突不自动升级严重度。

## 4. 严重度升级与降格

| 级别 | 升级条件 | 降格条件 | 处置边界 |
|---|---|---|---|
| S0 | 具体泄露、越权、错误操作风险且安全/正确性规则互斥 | 找到同时满足所有安全规则的安排 | 禁止路由绕过；修复或拒绝 |
| S1 | 同对象要求不可并存取值/顺序 | 条件、范围或顺序安排可同时满足 | 可条件覆盖、结构或合格 Router |
| S2 | 协调需要额外约束但可同时满足 | 等价则转 shared | 优先排序/结构 |
| S3 | 仅风格、语气、详略偏好张力 | 信号不足则 unconfirmed | 永不单独熔断；双模式 |

出现安全词不是 S0 充分条件。文本不完整时不得给确定 S0/S1。发现可行安排后必须降关系，不能维持强标签以保留戏剧性。

## 5. 极大团与确定性贪心检测

极大团是任意两节点均有指定类型边、且不能加入其他节点的集合；最大团是规模全局最大的团。本项目不声称求最大团。

算法：

1. 仅保留 S0/S1 `contradictory`、置信度至少 `high`、双方证据完整的无向边。
2. 节点按规范化技能名 Unicode 字典序排序。
3. 以每个节点为种子，按字典序遍历候选；仅当候选与当前团所有节点相邻时加入。
4. 若不能再加入节点，记录该极大团；对节点排序后的元组去重。
5. 只把至少三节点的团送入熔断复核。

报告必须写“近似检测，不保证找到全部极大团”。贪心可能遗漏团，因此未发现团不等于证明全局一致。

## 6. 熔断与对抗复核

熔断须同时满足：≥3 个不同技能、合格 S0/S1 contradictory 极大团、逐边原文、反方构造失败、置信度≥high。

反方提示固定为：“假设所有涉事规则都必须保留，请给出一个满足全部规则、且不违反任何安全要求的最小输出/执行安排。”

- 构造成功：降为 `entangled/shared` 或待人工，记录安排。
- 构造失败：逐项记录被违反规则 ID 与原因。
- S0：任何路由不得绕过。
- S1：可先尝试条件覆盖、结构或 Router。
- S3：不进入熔断。
- L2/L3：不得产生确定强不一致。

熔断报告仍须给不受影响独立组、零文本改动隔离和最小修复路径。

## 7. L1/L2/L3 降级

| 等级 | 触发 | 检查范围 | 禁止结论 |
|---|---|---|---|
| L1 | N≥4 | 从含 S1 contradictory 核心节点扩展三元组 | 不得声称已检查未枚举组合 |
| L2 | N>5 或输入超长 | 核心指令骨架；忽略代码、长示例、散文 | 不得确定强不一致 |
| L3 | 极端超长 | 指纹和元数据聚类 | 不得拒绝、熔断或声称语义矛盾 |

多条件同时成立时取 L3>L2>L1。记录剪枝规则、已查/未查组合和证据损失。

## 8. 指纹安全

指纹包含规范化触发词集合、章节标题序列、规则 ID 集 SHA-256。规则 ID 哈希固定对排序后、换行连接、无末尾换行的 UTF-8 文本计算。

- 指纹用于检索、聚类与基线变化提示，不是语义等价证明。
- 相同指纹不能证明基线语义未变；不同指纹也不能定位冲突原因。
- L3 命中只能输出“疑似冲突，待人工”。

## 9. Router 规则

决策表至少包含：输入条件、分发目标、排除场景、条件依据、无法判定时行为；另记录固定优先级。

1. 使用任务标签、扩展名、显式用户请求、diff 行数等可观察字段。
2. 禁止模糊条件；条件重叠时必须有全序优先级。
3. 用决策表覆盖默认场景，列出无法判定的输入。
4. 默认回退不得违反任何 S0；无法安全回退则 Router 失败。
5. S0 冲突不得路由绕过；S1 只有在任务边界真实可分时才可路由。
6. 子技能触发词须互斥，所有源规则有唯一归属。

## 10. 最小修复路径算法

候选操作：调整顺序、缩小范围、增加条件、拆分技能、改写触发、统一依赖 schema、经授权删除/替换、保持文本并隔离任务。

1. 枚举不改变安全边界的可行操作，再单独评估会改变安全边界的方案。
2. 过滤不能通过对抗复核或 Router 门槛的方案。
3. 依次按改动规则单元数、改动字符数、影响技能数、规范化修复文本字典序升序。
4. 安全边界改动的方案不得仅因成本小而排在安全修复之前。
5. 必须保留零文本改动隔离备选，并注明其适用范围和剩余风险。
6. 每条路径列步骤、规则 ID、预期结果、代价、风险、验证方式、用户确认需求。

删除或替换规则必须获得用户授权；分析器不得静默执行。

## 11. 增量与全量等价

保留 BASE 的规则 ID 和指纹，只给新增技能分配新 ID。检查新增×基线、新增×新增，以及新增对全局顺序、Router、共享写入、依赖和安全边界的影响。

- 不得跳过组合检查。
- 不能证明与全量一致时标 `incremental-equivalence: unverified`。
- 差量与全量不同，以全量为准并记录差异。
- 基线变更、指纹异常或缺失时退出增量并要求全量。
- 指纹相同不能单独证明规则语义未变。

## 12. 申诉与处置闭合

每个 S0/S1 强判定必须写：需要的反例、反例须满足的规则 ID、可改变结论的可观察事实、可能转成的新关系。

最终处置只能为 `keep/deduplicate/conditional-override/move-to-subskill/route/defer-human/exclude-with-reason`。所有源规则必须且只能出现一次；provenance、未纳入表和摘要有相同计数。
